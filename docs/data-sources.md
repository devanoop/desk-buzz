# Data sources — verification log

Checked 2026-08-23, per Phase 2's instruction to confirm each source's current download URL, format, and licence before writing its adapter. Re-verify before every ingestion run against a new release — these change between release years/quarters by design, and the adapters are built to fail loudly rather than silently accept a moved or reshaped file.

**Verification method note:** `bls.gov`'s main website (including its bulk `oesm{YY}all.zip` files) returns HTTP 403 to this session's tools — confirmed as genuine server-side bot-protection (Akamai) via both the `WebFetch` tool and a direct `curl` from Bash, not a tool-specific limitation. `dol.gov` and `ons.gov.uk` are directly reachable and were fetched for real. BLS's separate **Time Series REST API** (`api.bls.gov`) is _not_ behind the same block and was used instead — see §1. Nothing in this document is guessed; every URL below was hit directly this session (200 response, real content) except where explicitly marked otherwise.

## 5. India — explicit non-coverage

No adapter is implemented for India. Per the brief: _"there is no open, employer-level salary dataset for India... Do not fabricate Indian employer salary data, do not extrapolate US figures into INR, and do not present a bare currency conversion as local market data."_ MoSPI's Periodic Labour Force Survey (PLFS) exists and gives broad occupation/sector _bands_, not employer-level or percentile-distribution figures compatible with this pipeline's schema — evaluated and rejected as a `salary_benchmarks` source for this reason, not overlooked. The aggregation layer (`src/modules/ingestion/aggregate.ts`) has no default/fallback numeric value for an occupation+geography with zero real rows — it returns "no data," never a guess. The product's coverage-honesty UI requirement (say so plainly, fall back to user submissions) is a Phase 3 responsibility.

## 6. Cross-taxonomy occupation matching — a measured limitation, not a claimed solution

The occupation normalizer (`src/modules/ingestion/occupation-normalizer.ts`) maps free-text titles onto O\*NET SOC codes via exact/alias lookup, then two fuzzy fallbacks: character-level edit distance (good for typos on the _same_ title) and stemmed token overlap (needed for ASHE's UK titles, which are worded completely differently from O\*NET's — e.g. "Programmers and software development professionals" vs. "Software Developers"). Both DOL LCA (which ships real O\*NET SOC codes directly) and BLS OEWS (whose 6-digit codes map onto O\*NET's `.00` entries by a well-established, non-fuzzy convention) match reliably. **UK ASHE is the hard case**, because UK SOC 2020 and the US-built O\*NET taxonomy are independent classifications with no code-level crosswalk.

Measured against the real, full committed ASHE sample (52 real 4-digit-SOC rows): **13 of 52 (25%) cross-match** at the token-overlap thresholds currently set (0.75 overlap coefficient, ≥2 shared stemmed tokens, ≥6-char minimum token length). That threshold was tuned _down_ from a looser setting that matched 30/52 but included clear misclassifications (e.g. "Social workers" incorrectly matching "Social Scientists and Related Workers, All Other" on shared generic words) — the conservative setting was chosen deliberately, trading recall for not mislabeling a row, consistent with this whole pipeline's "suppress rather than guess" posture. Even at the conservative setting, at least one residual false positive is known ("Social workers" still matches "Social Scientists..." because both real, substantive-looking words happen to co-occur) — flagged here rather than hidden.

**This is a real limitation of a heuristic, not a solved problem.** A production system serious about UK coverage would want a maintained UK-SOC↔O\*NET (or UK-SOC↔ISCO) crosswalk table, or an embeddings-based matcher — both meaningfully better than string/token heuristics for this specific cross-national-taxonomy problem. That's flagged as a follow-up, not attempted here.
